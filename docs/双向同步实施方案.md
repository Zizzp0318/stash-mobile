# Stash 双向同步 · 实施方案

> 前置：`移动端设计方案.md` 里的路线选型已被本次决策取代 —— **只做原生、仓库公开、范围从「只读浏览」扩到「手机上传」**。
> 本文只写落地：协议、改动清单、不变量、验证方式。

---

## 1. 需求变更带来的三个结论

| 原假设 | 现在 | 后果 |
|---|---|---|
| 手机只读 | 手机要往库里**写** | 桌面端必须开一条写通道，并重新设计写权限鉴权 |
| PWA 打底 | 只要原生 | 去掉 Service Worker 那套，多出一个必须维护的编译流水线 |
| 「同步」= 浏览 | 「同步」含上传 | **仍然不做全量镜像**（理由见 §9），拆成「上传 + 浏览 + 按需下载」 |

最硬的一条：**Windows 编译不出 iOS 二进制**。所以不是「选个跨平台框架就能绕过」——Flutter / RN / Capacitor 一样要 macOS 出包。既然躲不掉，就直接上 SwiftUI（包小、手势和视频体验最好）。

## 2. 数据流

```
        ┌──────────── 读（原有） ────────────┐
iPhone  │  /api/assets /api/folders /tags     │  Windows
  ──────┤  /api/thumb /api/media (Range)      ├──────  Stash Desktop
        │                                     │        remote.ts (:5273)
        └──────────── 写（本次新增） ─────────┘
           /api/upload/begin → PUT → commit
                     ↓
              upload.ts ──→ importFiles()  ← 复用已有的导入管线
                              ├─ content_hash 去重
                              ├─ uniqueName 改名
                              ├─ 500 条一批的事务提交
                              └─ import:done 广播（桌面端自己会刷新）
```

**关键设计决策：上传不自己写库，而是把文件落进临时目录后交给 `importFiles()`。**
那 230 行里已经沉淀了去重、改名、事务回滚计数修正、事件广播四件事，各写一遍必然各错一遍。

## 3. 上传协议

```
1) POST /api/upload/begin        {"name":"IMG_0001.jpg","size":2481920,"folderId":12}
   ←  {"ok":true,"uploadId":"87186a9c...","offset":0,"name":"IMG_0001.jpg"}

2) PUT  /api/upload/{id}?offset=0        body: 裸字节（4 MB 一段）
   ←  {"ok":true,"received":4194304,"size":2481920}

3) ... 重复 2) 直到 received == size ...

4) POST /api/upload/{id}/commit
   ←  {"ok":true,"deduped":false,"assetId":128,"name":"IMG_0001.jpg","renamed":false}

   取消：DELETE /api/upload/{id}
```

### 两个必须守住的不变量

**① 重放幂等。** 断线重连时客户端从「上次确认的 offset」重发同一段。服务端若 `offset < received`
会先 `truncateSync(file, offset)` 再追加。没有这一步，文件会变成 `前段+前段+后段`——
**长度仍然等于 size，`size` 校验拦不住，但内容是坏的**，而且要到桌面端打开才发现。

**② 去重前置。** `commit` 先算 `content_hash` 查库，命中就直接返回那条 `assetId`（`deduped:true`），
连一次 4 GB 拷贝都不做。这就是「手机电脑同步素材」真正需要的语义：同一张照片传十次，库里只有一份。

### 为什么不用 multipart

Node 里手写 multipart 解析（boundary 切分、流式、异常中断）约 150 行，换来的只是「一个请求传一个文件」。
而三段式协议额外白送了断点续传，代码反而更短。

### 写权限为什么必须走请求头

`?t=` 放在 URL 里只适合 GET。如果写接口也接受查询串 token，任意网页都能对你局域网里的 5273
发一个**无预检**的跨站 POST（浏览器不会为该请求做 CORS 预检）→ CSRF。
自定义头会强制预检，而本服务不回应预检请求 → 浏览器侧直接死。

## 4. 桌面端改动清单

| 文件 | 类型 | 内容 |
|---|---|---|
| `electron/services/upload.ts` | **新增** | 会话管理、分段落盘、commit→`importFiles`、临时目录清理 |
| `electron/services/smoke-upload.ts` | **新增** | HTTP 层端到端冒烟（14 条断言） |
| `electron/services/remote.ts` | 修改 | 新增 `/api/ping`、`/api/upload/*`、`/api/asset/:id`；`authed()` 认 `X-Stash-Token`；`/api/pair` 返回 token；`/api/assets` 补字段 + `sort`/`type`；`stopRemote()` 清临时目录 |
| `electron/services/config.ts` | 修改 | `remoteAccess.allowUpload`（默认 true） |
| `electron/main.ts` | 修改 | 注册 `--smoke-upload` |
| `src/env.d.ts` / `src/stores/settings.ts` | 修改 | 类型与兜底同步 |
| `src/components/SettingsPanel.vue` | 修改 | 「允许手机上传素材」开关、安全说明改写 |

顺手修掉的一个老 bug：`/api/pair` 的 403 分支缺少 `return`，会继续执行到 `res.writeHead(200)`
触发 `ERR_HTTP_HEADERS_SENT`，用户看到的是「网络错误」而不是「配对码不对」。

### 临时目录为什么叫 `.stash-upload`

它必须落在库内（同盘才能 `mode:'move'` 走 rename 而不是再拷 4 GB），但库目录被 chokidar 监听。
`watcher.ts` 的 `isIgnoredAbs()` 对 `.stash*` 前缀一律忽略，且与 `reconcileLibrary` 共用同一判据，
所以半截文件不会被索引进库。**改名成 `upload-tmp` 就会立刻出问题**：上传中的文件被当成新素材。

## 5. iOS 端结构

```
AppModel ──┬── ConnectionStore   地址历史 / 配对 / Keychain / epoch
           ├── LibraryStore      分页 / 搜索 / 筛选 / 竞态防护
           └── UploadQueue       HEIC 转码 + 分段上传 + 重试 + 进度
```

几个刻意的选择：

- **`epoch` 计数器**而不是监听 `isConnected`：重连同一台机器时布尔量不变，但数据必须重拉。
- **`loadSeq` 竞态防护**：搜索时连打几个字，晚发出的请求可能先回来，列表会「跳回上一个关键词」。
- **按 `id` 定位队列项**，不用捕获的下标：`clearFinished()` 会在上传中删项，下标会整体前移。
- **`UIScrollView` 包 `UIImageView`** 做缩放，不写纯 SwiftUI 手势：双击以触点为中心放大 + 弹性边界
  + 惯性，系统级实现一行 `zoom(to:animated:)` 就够，手写要算一堆几何。
- **所有大图都降采样**（`CGImageSourceCreateThumbnailAtIndex`）：库里可能有 48 MP 的图，
  直接 `UIImage(data:)` 解出近 200 MB 位图，在手机上就是闪退。

## 6. HEIC：这件事必须由手机端做

桌面端 `importer.ts` 顶部有一整段注释在解释为什么 `EXT_TYPE` 里**没有 heic**：
那份预编译 sharp 的 libheif 不带 HEVC 编解码器，`heif({compression:'hevc'})` 直接抛错。

后果不是「导入失败」，而是更糟的：**导入成功、索引里有行、卡片永远空白且不报错**。
所以：

1. 服务端对 `.heic/.heif` 明确回 `415 ERR_UNSUPPORTED_TYPE`（**不能静默跳过**，静默跳过 =
   用户以为传上去了，其实什么都没发生）；
2. 客户端 `Transcoder.jpeg()` 在入队时把 HEIC 转成 JPEG，`maxPixel = 6000`（≈36 MP，
   覆盖绝大多数 12 MP 手机照片，只有 48 MP 的会缩一点）；
3. 转码时开 `kCGImageSourceCreateThumbnailWithTransform`，把 EXIF 方向**烤进像素**。
   少了这一步，竖着拍的照片在电脑端是躺倒的——很多转换器栽在这里。

## 7. 构建与签名

```
Windows（写代码）
   │  git push
   ▼
GitHub Actions · macos-14
   │  brew install xcodegen && xcodegen generate
   │  xcodebuild ... CODE_SIGNING_ALLOWED=NO
   ▼
Stash.ipa（未签名）
   │  gh run download --name Stash-ipa
   ▼
Windows · Sideloadly + 免费 Apple ID
   │  签名（7 天证书）→ 装机
   ▼
iPhone：信任开发者 + 开启「开发者模式」（iOS 16+ 必须，否则点开即闪退且无提示）
```

仓库里**不存 `.xcodeproj`**：Windows 上打不开二进制 plist，也合并不了冲突。
只存 `project.yml`，工程文件由 CI 生成。

⚠️ `project.yml` 刻意不用 XcodeGen 的 `info:` 块 —— 它会按 properties 反向生成 Info.plist，
把仓库里手写的那份（含 ATS / 本地网络 / 相册写入描述）覆盖掉。只通过 `INFOPLIST_FILE` 指向手写文件。

## 8. 怎么验证

```bash
# 桌面端：14 条断言，走真实 HTTP（fetch 打 127.0.0.1），不 mock
npm run build
env -u ELECTRON_RUN_AS_NODE ./node_modules/electron/dist/electron.exe . --smoke-upload
```

覆盖：ping 免鉴权 / 无凭据 401 / HEIC 415 / 分段上传 / **重放幂等** / 落盘位置 / DB 与磁盘 hash 一致 /
去重后行数不变 / 只带 `?t=` 的写请求 403 / `allowUpload=false` 生效 / 临时目录自我清理 / DELETE 取消。

这套冒烟当场抓到了一个真 bug：`/api/upload/begin` 的 `begin` 被 `split('/')` 当成 `:id`，
落到 405，而客户端只看到「返回的不是 JSON」，排查方向会彻底跑偏。

iOS 端目前只能靠 GitHub Actions 编译验证（Windows 上无法 `xcodebuild`）——
第一次跑 workflow 请预留几轮修编译错误的耐心。

## 9. 不做全量镜像的理由

「手机电脑同步素材」听起来像要两边一致，但这在这个产品里是负收益：

1. iOS 后台执行受限，免费签名又不支持推送 → 同步只能在前台发生，「永远一致」本来就是假的；
2. 删除传播和冲突解决是最容易吃掉一个项目全部时间的两件事，而素材库本质是
   「PC 为主库、手机为采集端 + 浏览端」；
3. 收益很小：用户真正在意的是「拍完的照片能不能进库」「在外面能不能翻两眼」。

所以范围钉死为：**上传（手机→电脑）+ 浏览（电脑→手机）+ 按需保存到相册**。
真要离线镜像，留到 v2，并且应该做成「手动下载整个目录」而不是后台持续同步。

## 11. 已知限制

- 上传只在**前台**推进；后台会给一段宽限期（`beginBackgroundTask`），之后暂停，下次打开续传。
- 网格是正方形而非瀑布流（瀑布流要自定义 Layout，收益不抵复杂度）。
- 无分享扩展：免费签名不支持 App Groups，扩展拿不到 token，要单独再配对一次。
- 免费证书 7 天失效，重签同 Bundle ID 不丢数据（Keychain 里的配对凭据也在）。
- 无 App 图标资源，系统会显示默认空白图标。
